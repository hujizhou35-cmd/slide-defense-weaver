# 问答与压力应对

## 基于项目推测问题

从用户材料出发选择问题：为什么值得做、为什么采用此方法、与已有工作区别、证据能支持多大结论、失败和不适用的情形、实际完成程度、个人与团队贡献、资源与落地条件。对竞赛关注规则和评分点，对论文答辩关注研究问题、方法、结果和局限。

每道题必须对应该项目的一个具体内容或薄弱点。不要把所有项目都套成“创新性、可行性、商业模式”三问。没有商业化要求的研究项目不强行讨论盈利。

先直接回答，再解释依据，最后给边界或下一步。答案引用的数字、功能、发表状态和个人经历必须可在材料或用户说明中找到。别把没有证据的问题包装成精巧回答。

## 压力问题的语气

不必认同提问中的不合理前提，也不先批评提问。用短而平实的话回答可以回答的部分，尽快落到工作、分工和可复核过程。

- 不说“您的问题非常专业/一针见血”作为所有回答的开头。
- 不说“英雄不问出处”“事实胜于雄辩”等反击口号。
- 不用“我们还有很多不足”回避明确的事实问题。
- 不承诺当场展示不存在的代码、原始记录、专利或实验结果。
- 质疑有事实依据时承认具体不足；不要把所有尖锐问题都判为无理取闹。

## 必须覆盖的两类问题

### “你的老师这么年轻，怎么可能做出来这些？”

关切通常在于能力和成果真实性。直接谈工作依据，不评论评委，也不吹捧导师。

可改写的表达骨架：

> 这项工作可以从实际完成的内容来判断。我们可以具体说明已经完成的部分、分工和验证过程。

随后只能补充**已经确认存在**的内容和证据，例如老师具体负责什么、学生完成了什么、哪些过程可展示。分工未知时先问，不能为了完整而代填；没有可展示记录时也不能承诺提供。无需对“年轻是否有能力”展开争辩。

### “这些是你做的吗？”

关切是个人贡献和理解程度。回答应逐项划清自己、队友、导师及已有工具的边界。

可改写的表达骨架：

> 这是团队共同完成的。我本人主要负责……；……由队友负责，老师在……环节提供指导。关于我负责的部分，我可以进一步说明具体做法和遇到的问题。

仅在真实分工确实如此时使用。不要求所有项目都采用“老师仅指导”这一设定；导师实际参与设计或实现就如实说明。第三方库、开源模型和AI辅助也不能说成全部从零自主开发。

以上是准备时的表达骨架，不是未经核实即可交付的答案。最终可朗读回答不能保留省略号或空白分工。

## 按项目增补的压力情境

| 可能的问题 | 回答方向 |
| --- | --- |
| “这不就是把现成工具拼在一起吗？” | 先承认使用的已有工具，再说清自己确实完成的新增工作及证据；没有独立算法创新就不宣称有 |
| “是不是AI帮你做的，你自己根本不懂？” | 如实说明AI使用范围、本人检查和完成的部分，能够解释的细节才说能解释 |
| “样本这么少，有什么意义？” | 解释研究阶段、能支持的结论和不能支持的范围，不把小样本说成有代表性 |
| “你的结果这么好，是不是挑出来的？” | 说明真实的数据划分、评价和报告流程；材料缺失时先核实，不能编造盲测或外部验证 |
| “给你更多时间是不是也做不出来？” | 说明已完成工作与尚未完成的具体环节，下一步计划不伪装成已兑现承诺 |
| “如果现场演示失败怎么办？” | 说明已确认存在的备用展示和可复核结果，区分演示故障与功能未完成 |

从中选择相关情境，不全部机械搬入。准备文件可提醒语速、停顿和避免争辩，但这些提示与可朗读回答分开。
