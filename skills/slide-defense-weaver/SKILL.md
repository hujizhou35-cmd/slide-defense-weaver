# Slide Defense Weaver

让整场答辩讲完一个故事，每页推动故事向前。先理解项目，再确认叙事和页序，最后写稿。默认中文，按用户要求切换语言；优先适配竞赛，但不把商业路演结构强加给科研或论文答辩。

## 1. 首轮先确认时间与场景

先检查对话中已经明确的信息，只追问缺失项。首轮先问正式陈述时长、提问时长，以及二者分别计时还是共享总时长。没有提问环节可以明确为零，不能把“未知”当作零。此时不直接读取材料并抢先写稿。

同时确认答辩类型、评委背景和现有规则或评分要求；用户不了解评委背景时如实记录，不强迫其猜测。若只给总时间，追问陈述与问答如何分配。不能自行挪用问答时间。涉及视频或演示时，确认播放/操作时长、是否计入陈述、是否边播边讲；阅读后才发现媒体则补问。

开场可以简洁地问：“正式陈述和评委提问分别有几分钟，是否分开计时？这是哪类答辩，有评分要求或评委背景说明吗？如果安排视频或演示，它们是否占用陈述时间？”不要重复索要已知信息。

## 2. 找齐并理解材料

时间边界明确后，查找用户指定附件或当前工作路径中的PPT和项目计划书、申报书、论文或等价项目说明。优先读取明确指定的文件；存在多个可能版本就请用户选定，不按文件名猜“最新版”，不把不同案例混成一个项目。缺少任一必要材料立即索要。用户明确以其他充分说明代替计划书时，记录替代来源和局限。

完整阅读项目材料，逐页检查PPT文字、图表、图片、备注、隐藏页、视频和演示安排。可用 [辅助脚本](references/tooling.md) 提取真实页序、文本和媒体清单，但必须另外渲染或打开PPT看页面。提取不到文字不等于空白页或章节页；备注也不能覆盖画面上的事实。无法读取的关键内容须请用户补充，不能声称已理解。

维护轻量工作记录：材料版本、时间与规则、关键主张及来源位置、冲突与待确认项、用户选择、最终PPT对应关系。不需要把内部记录全部塞进讲稿。数字、指标、贡献、完成状态发生实质冲突时列明两个出处立即追问；可继续处理不依赖该答案的部分，但不能选一个数字当定稿事实。

如存在团队介绍，明确询问“一句话略过、详细介绍，还是规则禁止展示”。简略模式不擅自追加成果；详讲须有分工与成果依据。禁止展示时同时检查封面、姓名、学校、导师、照片、标识及文件备注等可能身份信息，按实际比赛规则处理。若规则禁止而PPT仍含相关信息，说明必须先处理这些页面；不能把“不读出来”当作合规展示。

首次组织故事时阅读 [案例与衔接方法](references/storycraft.md)。参考其方法，不继承案例数字、主张、局限或原有页面处理。

## 3. 先给用户看故事和页序建议

正式稿之前必须先展示：

1. 一句话说明希望评委最终记住什么。
2. 一段连贯的完整故事，说明问题如何引出方案、方案如何得到证据、证据如何支撑价值。不能只列章节标题。
3. 逐页作用表：实际页码/主题、这一页回答的问题、承接与推进、详讲/简讲/无声跳过/备用、预估重点。
4. 具体调整建议：涉及的原页码、移动/合并/删减或保留方式、当前问题、调整理由、对时间和必要内容的影响。合并须说明保留什么、怎样讲，不能只说“更紧凑”。没有问题就建议保留。

检查背景过长、重复、逻辑跳跃、证据过晚和重点失衡。按项目实际和评分要求决定顺序，不把某一固定故事模板当唯一正确答案。已获认可的事实冲突仍需解决；故事好听不抵消证据问题。

**在这里让用户确认故事及处理路线，等待答复后再写正式稿。** 这是用户指定的工作流程，不要把沉默当确认。用户可以部分接受、要求重写故事，或明确保留全部原序。

## 4. 锁定实际PPT后写稿

- **先改PPT再出稿：** 询问由用户自己修改还是委托AI修改副本。用户修改后获取新文件；AI仅落实确认的修改，保留原件。合并、重排后检查内容、布局、备注、隐藏状态、媒体和跳转。确认最终文件及实际顺序，保留原页到新页的对应。没有修改完成的页面不能当成已存在。
- **当前PPT直接出稿：** 使用当前真实页序，通过内容承接改善表达；说明仍影响叙事的结构限制。不暗中重排、不假设观众已看到后面的证据、不引入未经确认的跳页演示。

使用环境中可用的演示文稿编辑能力完成获准的PPT修改。若无法可靠编辑或验证，说明具体限制并请用户修改或选择当前版本出稿，不重建整套PPT冒充原稿修改完成。

把确认后的全篇故事写成连贯讲述，再按已确定的页面任务落实。每个实际页面必须有条目，页码取物理页序而非页面上印刷的数字。正文保持与画面同步，不能先把整段写好再随意切页。

### 写作硬要求

- 每张内容页接住前文已建立的信息，再增加解释、证据或推进。不能靠反复“接下来”“下面介绍”掩盖段落彼此独立。
- 使用自然、正式、便于听懂和复述的句子。少写报告式长句、抽象套话和标题复读；也不使用闲聊口气。技术细节以评委需要理解的程度为准。
- 纯数字和纯章节页标注“无声翻过”，朗读正文为空。衔接放在前后内容页。含核心信息的内容页不能因为大标题而被误判为章节页。
- 连续多页共同表达一个意思，也分别标记每页讲述、停顿或翻页，不使用“第21—23页共一段”而失去操作对应。隐藏/备用页同样留条目，注明不进入主讲，除非用户确认启用。
- 团队按确认方式写。简略模式可以只说“本项目分工明确，团队架构合理。”；不把导师或团队成果自动说成个人贡献。
- 区分已实现、已验证、初步观察与未来计划。不能迁移案例事实、把相关性写成因果，或用“首个”“全面超越”等措辞代替依据。
- 默认保留有感染力的结尾，回扣开头的真实问题、服务对象和项目价值。升华应由内容自然得出，不强套政策口号，不夸大成果；科研答辩也可用克制而有记忆点的表达收束。

按 [交付与时间规则](references/deliverables.md) 分配时长。开场、结尾、媒体、演示、停顿和翻页都计入；问答独立。扣除媒体/演示占用后默认预留约10%缓冲。无个人实测语速时可暂用240中文字符/分钟做粗估，并明确这是排稿参数而非达标证明。英文、缩写、数字读法和技术讲解须单独校准。超时先删重复、次要信息，再调整页面轻重，不要求用户靠加速念稿达标。

## 5. 准备两类问答

读取 [问答与压力应对](references/qa-guide.md)。默认交付项目问答和压力问答两个独立文件，不再询问是否需要。题目按材料薄弱点和评委关注点选择，不按固定数量凑题。

普通问答写清问题、评委关心什么、直接回答、追问展开、依据和练习优先级。压力问答至少覆盖“导师这么年轻，怎么可能做出来”和“这些是你做的吗”，并结合项目增补。回答不卑不亢，直接回应，以真实分工和过程证据落地，不反讽、不讨好、不虚构能力或贡献。

关键回答缺依据时先追问。仍未获得事实的条目明确标为待确认准备项，并与可直接使用的回答分开；不能把方括号模板当成已核实口播答案。

## 6. 审查并交付

使用 [交付结构](references/deliverables.md) 生成三个独立Word文件：`逐页答辩稿.docx`、`评委问答准备.docx`、`压力问答应对.docx`。不覆盖既有版本；输出目录使用当前任务的独立目录。不得用Markdown替代用户预期的Word并声称完成。

交付前逐项完成：

1. 核对最终PPT版本、逐页对应、全部页面覆盖以及无声页无正文。运行辅助检查；报错修复后重跑。
2. 将每个有讲述页面的结尾与下一个有讲述页面的开头连读，跨过无声页仍应自然。再去掉页码、提示和标题，通读完整讲稿。若每段单独看都像开场，要改写内容关系，而非仅换连接词。
3. 核对语气、事实、时间、团队规则以及问答是否真正回应问题。保留用户未确认事项，不给其编答案。
4. 使用当前环境的文档工具生成Word，渲染成页面图片并逐页打开检查。修复缺字、截断、孤立标题、拥挤和提示混入正文，再重新渲染。不要把“文件生成成功”当作视觉验收。

环境缺少必要的读取、编辑或渲染能力时明确说明阻碍，提供可继续处理的部分，并索要所需材料或选择；不能悄悄跳过检查或宣称三个文件已验收。内部JSON、渲染图片、测试日志默认不作为用户交付。

最终只需清楚链接三个Word文件，注明预计陈述时间、采用的PPT版本和影响使用的待确认项。实测排练未进行时，不承诺一定不超时。
